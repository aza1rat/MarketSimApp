## Общие принципы
- Приложение делится на логические модули, каждый из которых отвечает за строго ограниченную функциональность (фичу, слой, утилиту).
- Каждая фича (feature) представляется **двумя** Gradle-модулями:
    - `:features:feature-name:api` – содержит только интерфейсы, модели данных (DTO), контракты, которые могут использоваться другими модулями.
    - `:features:feature-name:impl` – содержит реализацию, внутренние классы, DI-компоненты, специфичные для фичи.
- Модули **не должны** зависеть друг от друга циклически.
- Внешние зависимости (библиотеки, фреймворки) должны быть инкапсулированы внутри `impl`-модуля, если они не являются частью публичного API. [OP-1]
- Модули, предоставляющие API, должны быть максимально легковесными (без лишних зависимостей).

> [OP-1]
> Все внешние зависимости должны быть инкапсулированы в модуле реализации (`impl`), за исключением случаев, когда библиотека предоставляет типы (классы, интерфейсы, аннотации), непосредственно используемые в публичном контракте API-модуля. В таких случаях зависимость может быть добавлена в `api`-модуль с использованием конфигурации `api` (если типы должны быть видны потребителям) или `compileOnly` (если достаточно для компиляции, а рантайм-реализация будет предоставлена другим способом). Запрещено добавлять в `api`-модуль зависимости, не являющиеся частью публичного контракта

## Структура каталогов и именование модулей
- Все модули используют строчные буквы, слова разделяются дефисом (Kebab-case): `build-logic`
- Путь к модулю соответствует его иерархии (название модуля): `:features:auth:api`, `:core:network`.
- Имена модулей должны отражать их суть и быть уникальными в пределах проекта.

```
project-root/
├── app/                          # основной сборщик (application)
├── builg-logic/                     # общие конфигурации, версии, плагины
├── core/                         # общие компоненты (независимые от фич)
│   ├── network/
│   ├── database/
│	├── ui/
|   ├── navigation/
├── features/                     # все фичи
│   ├── some-feature-1/
│   │   ├── api/
│   │   └── impl/
│   ├── some-feature-2/
│   │   ├── api/
│   │   └── impl/
│   └── ...
```


## Зависимости между модулями
### Правила видимости
- Модуль `impl` **обязан** зависеть от своего `api` через конфигурацию `implementation` (или `api`, если требуется проброс).
- Любой другой модуль (включая `app`, другие фичи, core) **может** зависеть только от `api`-модуля фичи. Зависимость от `impl` **запрещена**.
- Модули `api` не должны зависеть от `impl` или других `impl`-модулей.
- Модули `core` не должны зависеть от фичей (обратная зависимость запрещена).
### Конфигурации зависимостей
Использовать следующие конфигурации Gradle:
- `implementation` – для зависимостей, не раскрываемых наружу (внутренняя реализация).
- `api` – когда зависимость должна быть видна транзитивно для потребителей модуля (использовать с осторожностью, только в `api`-модулях, где зависимость используется непосредственно в контракте).
- `compileOnly` – для аннотаций, библиотек генерации кода, процессоры аннотаций
- `testImplementation` – для тестов внутри модуля.
- `androidTestImplementation` – для инструментированных тестов.
### Запрет циклических зависимостей
Сборка должна завершаться с ошибкой при обнаружении цикла


## Управление зависимостями и версиями
### Версионирование зависимостей
Использование файла `libs.versions.toml`
### Convention-плагины
Для каждого типа модуля (application, kotlin-library, android-library) создать convention плагин, который применяет соответствующие базовые плагины
Convention плагины:
- Устанавливающие общие параметры: `compileSdk`, `minSdk`, `targetSdk`, `kotlinOptions`, `buildFeatures`, `defaultConfig` и т.д.
- Включают единые правила линтинга, форматирования, тестирования

## Оптимизация сборки
- Использовать **Configuration Cache** – включить в `gradle.properties`.
- Настроить параллельную сборку (`org.gradle.parallel=true`).
- Минимизировать количество задач, выполняемых при инкрементальной сборке за счёт правильного разделения модулей.
- Избегать динамических версий зависимостей (использовать фиксированные).

## Ограничения и проверки
Все модули должны корректно собираться командой `./gradlew assembleDebug` без ошибок.
**Ограничение на количество модулей:** Количество модулей, настроенных как `install-time` (устанавливаемые при инсталляции), должно быть **10 или менее**. Превышение этого лимита может привести к проблемам при сборке и доставке фич
Раздел Зависимости между модулями и проверять через `ArchUnit`
Проверка неиспользуемых зависимостей в модулях
**Минимизация `compileClasspath`:** Запрещено добавлять тяжелые библиотеки (например, Room, Retrofit) в `api` зависимости, если они не являются частью публичного интерфейса. Это заставляет Gradle перекомпилировать все зависимые модули при изменении реализации, даже если интерфейс не менялся
**Изоляция внедрения зависимостей (DI):** DI-логика (например, Dagger/Hilt компоненты) должна быть изолирована внутри `impl` модулей. `app` модуль выполняет только финальное связывание, но не должен содержать код инициализации конкретных фич.
