# Data layer: работа с API и обработка данных

## 1. Назначение data-слоя

Data layer отвечает за получение данных из внешних источников, преобразование их в формат, необходимый приложению, и реализацию контрактов, определённых в domain layer.

В проекте сетевое взаимодействие реализовано с помощью **Ktor Client**, сериализация JSON — с помощью **Kotlinx Serialization**, а внедрение зависимостей — с помощью **Hilt**.

Data layer не должен раскрывать domain layer детали HTTP-запросов, Ktor, сетевых DTO и формата ответов сервера.

### Основные обязанности

- Выполнение запросов к API.
- Передача параметров и тела HTTP-запросов.
- Десериализация JSON в DTO.
- Обработка успешных и ошибочных HTTP-ответов.
- Преобразование сетевых DTO в доменные модели.
- Реализация интерфейсов репозиториев из domain layer.
- Передача результата выполнения операции в presentation layer через domain layer.

## 2. Структура сетевого слоя

В сетевом взаимодействии участвуют следующие компоненты.

| Компонент | Ответственность                                            |
|---|------------------------------------------------------------|
| `AuthApi` | Контракт запросов авторизации                              |
| `AuthApiImpl` | Реализация HTTP-запросов через Ktor                        |
| `NetworkClient` | Контракт клиента                                           |
| `AuthNetworkClient` | Вызов API и передача ответа на обработку                   |
| `HttpClientHolder` | Хранение публичного и авторизованного `HttpClient`         |
| `NetworkModule` | Настройка и предоставление сетевых зависимостей через Hilt |
| `Response` | DTO для успешных и ошибочных ответов API                   |
| `HttpResponse.toResponse<T>()` | Преобразование HTTP-ответа в соответствующий DTO           |
| `safeApiCall` | Централизованная обработка ошибок сетевого вызова          |
| `NetworkResult` | Представление результата сетевой операции                  |
| `LoginRequestDto` | Данные запроса входа                                       |
| `LoginResponseDto` | Данные ответа при входе                                    |

DTO для регистрации и получения текущего пользователя следуют аналогичному назначению: `RegisterRequestDto`, `MeRequestDto`.

## 3. Как проходит сетевой запрос

При выполнении запроса авторизации взаимодействие компонентов выглядит следующим образом:

1. Вызывающий слой инициирует операцию через domain layer.
2. Реализация репозитория в data layer вызывает `AuthNetworkClient`.
3. `AuthNetworkClient` выбирает соответствующий запрос и вызывает метод `AuthApi`.
4. `AuthApiImpl` формирует HTTP-запрос и выполняет его через нужный `HttpClient`.
5. Ktor получает ответ сервера и при необходимости десериализует JSON.
6. `HttpResponse.toResponse<T>()` преобразует ответ в `Response.ResultResponseDto<T>` или `Response.FailedResponseDto`.
7. `safeApiCall` обрабатывает ошибки выполнения запроса и формирует `NetworkResult`.
8. Data layer преобразует полученные DTO в доменные модели и возвращает результат через интерфейс репозитория.
9. Domain layer передаёт результат вызывающему сценарию использования, а presentation layer отображает состояние интерфейса.

Упрощённая схема:

`Presentation → Domain → Repository → AuthNetworkClient → AuthApi → AuthApiImpl → Ktor Client → API`

Ответ проходит в обратном направлении с обработкой ошибок и преобразованием моделей на соответствующих уровнях.

## 4. Настройка Ktor Client

Настройка сетевых клиентов находится в `NetworkModule`.

В конфигурации клиента используются следующие компоненты:

- **Engine (`CIO`)** — отвечает за фактическое выполнение HTTP-запросов. В проекте движок выбирается при создании `HttpClient`.
- **`HttpTimeout`** — задаёт ограничения времени ожидания соединения, ответа и сокетных операций.
- **`ContentNegotiation`** — обеспечивает преобразование тела HTTP-ответа в Kotlin-объекты и сериализацию тела запроса.
- **`Kotlinx Serialization`** — предоставляет сериализаторы для DTO, помеченных аннотацией `@Serializable`.
- **`Auth`** — плагин. Используется авторизованным клиентом для Bearer-аутентификации.

Настройка `ignoreUnknownKeys = true` позволяет игнорировать поля ответа сервера, которые не объявлены в DTO.

### Публичный и авторизованный клиенты

`HttpClientHolder` предоставляет два клиента:

- `@PublicHttpClient` — для запросов, которым не требуется авторизация.
- `@AuthorizedHttpClient` — для защищённых запросов, выполняемых с использованием Bearer-токена.

Квалификаторы позволяют Hilt различать два экземпляра `HttpClient` одного типа.

Выбор клиента должен происходить при реализации конкретного API-метода. Не следует вручную создавать новый `HttpClient` для каждого запроса: клиенты рассчитаны на повторное использование.

## 5. API-интерфейс и его реализация

### `AuthApi`

`AuthApi` определяет контракт сетевого взаимодействия с API авторизации. Он описывает доступные операции:

- получение ответа на запрос входа;
- получение ответа на запрос регистрации;
- получение данных текущего пользователя.

Интерфейс позволяет отделить описание операций от их реализации.

### `AuthApiImpl`

`AuthApiImpl` реализует `AuthApi` и отвечает за детали HTTP-взаимодействия:

- выбор URL и HTTP-метода;
- передачу параметров и тела запроса;
- установку `Content-Type` для JSON-тела;
- выполнение запроса через соответствующий клиент;
- получение `HttpResponse`.

Базовый URL и пути эндпоинтов следует хранить централизованно, а не дублировать в разных местах проекта.

Пример формирования запроса:

```kotlin
clientHolder.publicClient.post(BASE_URL) {
    url {
        protocol = URLProtocol.HTTP
        path(LOGIN_PATH)
    }
    contentType(ContentType.Application.Json)
    setBody(loginRequestDto)
}
```

Здесь `setBody()` передаёт DTO в качестве тела запроса. Для его сериализации должна быть настроена сериализация JSON.

## 6. DTO и доменные модели

DTO (Data Transfer Object) используются для передачи данных между приложением и сервером. Их структура определяется контрактом API, а не требованиями интерфейса приложения.

## 7. Обработка ответов API

В проекте используется sealed-класс `Response` с двумя вариантами ответа.

### Успешный ответ

```kotlin
@Serializable
data class ResultResponseDto<T>(
    val success: Boolean,
    val message: String?,
    val data: T?,
    val errors: List<String>?
) : Response()
```

`ResultResponseDto<T>` описывает успешный ответ API, содержащий данные типа `T`, сообщение и возможные ошибки.

### Ошибочный ответ

```kotlin
@Serializable
data class FailedResponseDto(
    val type: String?,
    val title: String?,
    val status: Int?,
    val detail: String?,
    val errors: JsonElement?
) : Response()
```

`FailedResponseDto` описывает структуру ошибочного ответа, например ответ с HTTP-статусом `400` или `401`, если сервер возвращает тело соответствующего формата.

### Преобразование `HttpResponse`

Расширение `HttpResponse.toResponse<T>()` выбирает DTO в зависимости от HTTP-статуса:

- успешный статус — `ResultResponseDto<T>`;
- неуспешный статус — `FailedResponseDto`.

Важно различать HTTP-статус и поле `success` внутри JSON. HTTP-статус определяет результат на уровне протокола, а `success` — содержимое тела ответа.

## 8. Централизованная обработка ошибок

`safeApiCall` используется для унификации обработки исключений, возникающих при выполнении сетевых операций.

`NetworkResult` представляет результат выполнения операции и позволяет передавать его вызывающему коду в согласованном формате.

При обработке запросов необходимо различать несколько категорий ошибок:

- **Ошибки соединения** — например, отсутствие соединения с сервером или тайм-аут.
- **Ошибки HTTP** — сервер вернул неуспешный статус, например `401 Unauthorized`.
- **Ошибки десериализации** — тело ответа не соответствует ожидаемому DTO или для типа не найден сериализатор.
- **Другие исключения** — ошибки, не относящиеся к предыдущим категориям.

## 9. Авторизованные запросы

Для защищённых эндпоинтов используется `@AuthorizedHttpClient`, настроенный с плагином `Auth` и Bearer-аутентификацией.

При выполнении запроса клиент должен получить актуальный токен и передать его в заголовке:

```http
Authorization: Bearer <access_token>
```

Публичный клиент предназначен для операций, которым токен не требуется, например входа пользователя.

Если защищённый эндпоинт возвращает `401 Unauthorized`, следует проверить:

1. Выполнен ли вход и получен ли токен.
2. Сохранён ли токен в используемом хранилище.
3. Доступен ли токен авторизованному клиенту.
4. Передаётся ли заголовок `Authorization`.
5. Не истёк ли срок действия токена.

Само наличие плагина `Auth` не гарантирует успешную авторизацию: необходимо корректно настроить получение токена и его передачу клиенту.

## 10. Как добавить новый запрос

При добавлении нового эндпоинта рекомендуется придерживаться следующего порядка.

### Шаг 1. Создать DTO

Определить DTO запроса и ответа в data layer согласно контракту API. Для классов, которые сериализуются или десериализуются через Kotlinx Serialization, использовать `@Serializable`.

### Шаг 2. Добавить метод в API-интерфейс

В `AuthApi` или другом соответствующем API-интерфейсе объявить новый метод, возвращающий `HttpResponse` либо другой предусмотренный архитектурой тип.

### Шаг 3. Реализовать метод

В соответствующем классе реализации, например `AuthApiImpl`, определить HTTP-метод, путь, параметры, заголовки и тело запроса.

Для защищённого эндпоинта использовать авторизованный клиент, для публичного — публичный.

### Шаг 4. Подключить обработку результата

В `FeatureNetworkClient` добавить обработку нового типа запроса и передать вызов через `safeApiCall`, используя соответствующий парсер ответа.

### Шаг 5. Преобразовать DTO в доменную модель

Если данные используются бизнес-логикой, преобразовать DTO в доменную модель и вернуть её через реализацию репозитория.

### Шаг 6. Обновить domain layer при необходимости

Если операция новая, определить её контракт в domain layer — например, через интерфейс репозитория и use case. Не переносить HTTP-логику в domain layer.

### Шаг 7. Проверить результат

Проверить успешный ответ, ошибочный HTTP-статус, некорректное тело ответа и отсутствие соединения.

## 11. Правила организации data layer

При дальнейшей разработке следует придерживаться следующих принципов:

1. **Не выполнять HTTP-запросы из ViewModel напрямую.** Запрос должен проходить через предусмотренные архитектурой слои.
2. **Не использовать сетевые DTO в domain layer.** Преобразовывать их в доменные модели на границе data/domain.
3. **Не создавать `HttpClient` на каждый запрос.** Использовать экземпляры, предоставляемые через `NetworkModule` и `HttpClientHolder`.
4. **Не смешивать ошибки HTTP и ошибки соединения.** Для них нужны разные варианты обработки.
5. **Не предполагать, что каждый ошибочный ответ содержит JSON.** Формат ответа необходимо проверять перед десериализацией.
6. **Не дублировать настройку Ktor.** Общие таймауты, логирование, сериализацию и авторизацию конфигурировать централизованно.
7. **Не хранить секреты и токены в логах.** При отладке учитывать, что сетевое логирование может раскрыть заголовки авторизации и содержимое запросов.

## 12. Жизненный цикл `HttpClient`

`HttpClient` создаётся и предоставляется через DI. Клиенты предназначены для многократного использования, поэтому закрывать их после отдельного запроса не следует.

`HttpClientHolder` содержит метод `close()`, который закрывает оба клиента. Его нужно вызывать только тогда, когда соответствующие клиенты больше не используются, например в контролируемом жизненном цикле тестов.

Не следует полагаться на `Application.onTerminate()` для закрытия клиентов: этот callback обычно не вызывается при штатном завершении процесса на реальном Android-устройстве.
