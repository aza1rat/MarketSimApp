# Data layer: API и обработка данных

## Назначение

Data layer выполняет запросы к API, обрабатывает ответы и ошибки, а
также преобразует сетевые DTO в доменные модели. Domain layer не зависит
от Ktor, HTTP и сетевых DTO.

В проекте используются Ktor Client, Kotlinx Serialization и Hilt.

## Основные компоненты

| Компонент                             | Ответственность                                                                           |
|---------------------------------------|-------------------------------------------------------------------------------------------|
| `FeatureApi` / `FeatureApiImpl`       | Описывают операции API фичи и формируют `NetworkRequest`                                  |
| `NetworkRequest`                      | Содержит HTTP-метод, путь, фдаг авторизации и тело запроса                                |
| `NetworkExecutor`                     | Контракт выполнения сетевого запроса                                                      | 
| `KtorNetworkExecutor`                 | Выполняет запрос через Ktor, добавляет токен при необходимости и передаёт ответ на разбор |
| `NetworkModule`                       | Предоставляет singleton `HttpClient` через Hilt                                           |
| `Response`                            | DTO для успешного и ошибочного ответа сервера                                             |
| `HttpResponse.toResponse(serializer)` | Десериализует тело ответа в соответствующий вариант `Response`                            |
| `safeApiCall`                         | Централизованно обрабатывает ошибки сетевого вызова                                       |
| `NetworkResult`                       | Представляет результат сетевой операции                                                   |

## Как проходит запрос

1. Presentation layer вызывает операцию через domain layer.
2. Реализация репозитория в data layer обращается к клиенту API.
3. Клиент API формирует `NetworkRequest` и передаёт его в
   `NetworkExecutor` вместе с сериализатором ожидаемого DTO.
4. `KtorNetworkExecutor` выполняет HTTP-запрос через общий
   `HttpClient`.
5. Если `request.isAuthorized == true` и токен доступен, исполнитель
   добавляет заголовок `Authorization: Bearer <token>`.
6. `safeApiCall` вызывает парсер `HttpResponse.toResponse(serializer)`
   и преобразует результат в `NetworkResult`.
7. Data layer при необходимости преобразует DTO в доменную модель и
   возвращает результат через репозиторий.

Упрощённо:

`Presentation → Domain → Repository → AuthNetworkClient / AuthApi → NetworkExecutor → Ktor Client → API`

Ответ проходит обратно через разбор ответа, обработку ошибок и
преобразование моделей.

## Настройка Ktor Client

`NetworkModule` предоставляет один singleton `HttpClient`. В его
конфигурации используются:

- `CIO` --- движок выполнения HTTP-запросов;
- `HttpTimeout` --- ограничения времени ожидания;
- `ContentNegotiation` с Kotlinx Serialization --- сериализация и
  десериализация JSON;
- `ignoreUnknownKeys = true` --- игнорирование полей ответа,
  отсутствующих в DTO.

## Выполнение запроса и авторизация

`KtorNetworkExecutor` выбирает HTTP-операцию по `request.method`. Общая
настройка запроса вынесена в отдельную функцию, чтобы не дублировать
добавление токена для разных методов.

Для авторизованного запроса добавляется заголовок:

``` http
Authorization: Bearer <access_token>
```

Если токена нет, заголовок не добавляется. Такой случай нужно учитывать
в обработке ответа, поскольку защищённый эндпоинт может вернуть
`401 Unauthorized`.

Базовый URL хранится централизованно. При формировании адреса необходимо
корректно объединять `BASE_URL` и `request.path`, не допуская двойных
или отсутствующих `/`.

## DTO и обработка ответов

DTO отражают контракт API и относятся к data layer. Их не следует
передавать в domain layer.

`Response` содержит два варианта:

- `ResultResponseDto<T>` --- ответ с полями `success`, `message`,
  `data` и `errors`;
- `FailedResponseDto` --- описание ошибочного ответа с полями `type`,
  `title`, `status`, `detail` и `errors`.

`HttpResponse.toResponse(serializer)` использует переданный
`KSerializer<T>`, чтобы десериализовать `data` в нужный DTO, не создавая
зависимости сетевого слоя от конкретных DTO feature-модуля. В текущем
парсере наличие поля `success` в JSON используется для выбора варианта
ответа.

`safeApiCall` централизует обработку исключений. Следует различать
ошибки соединения и тайм-ауты, HTTP-ошибки, ошибки десериализации и
прочие исключения.

## Как добавить новый запрос

1. Создать DTO запроса и ответа в data layer и пометить сериализуемые
   классы `@Serializable`.
2. Добавить операцию в соответствующий API-контракт и сформировать
   `NetworkRequest`.
3. Передать запрос в `NetworkExecutor` вместе с сериализатором
   ожидаемого DTO.
4. Указать `isAuthorized = true`, если эндпоинту нужен Bearer-токен.
5. При необходимости преобразовать DTO в доменную модель и вернуть
   результат через репозиторий.
6. Проверить успешный ответ, ошибочный ответ, некорректное тело,
   отсутствие токена и отсутствие соединения.
